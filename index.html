Detailed Database Testing Analysis

The screenshots in the gallery above demonstrate a comprehensive approach to database testing. Below is a breakdown of what is happening in each step, the purpose of the test, and how it validates the database structure.

1. Schema Inspection (DESCRIBE)

What is happening: Running DESCRIBE users; and DESCRIBE usage_logs;.

Why: To verify the database schema, checking that tables were created with correct columns, data types (INT, VARCHAR, TIMESTAMP), and default values.

Validation: Proves the Python script (setup_database.py) successfully created the tables exactly as designed.

2. Verifying Primary Keys

What is happening: Querying INFORMATION_SCHEMA.KEY_COLUMN_USAGE for constraints named 'PRIMARY'.

Why: To ensure every table has a Primary Key defined, guaranteeing uniqueness for each row.

Validation: Confirms that all 6 tables (users, chat_sessions, etc.) have active Primary Keys, enforcing data integrity at the table level.

3. Verifying Foreign Keys

What is happening: Querying INFORMATION_SCHEMA for REFERENCED_TABLE_NAME (Foreign Keys).

Why: To verify that relationships between tables (e.g., messages belonging to chat_sessions) are correctly mapped.

Validation: Proves the database is relational and prevents orphaned data (e.g., a message cannot exist without a valid session).

4. Duplicate Email Test (Negative)

What is happening: Attempting to insert 'alice@example.com' a second time.

Why: To test the UNIQUE constraint on the email column.

Validation: The database rejects the insert with Error 1062. Duplicate entry. This proves the database prevents duplicate users (Pass).

5. Invalid Plan Test (Negative)

What is happening: Trying to insert a user with plan = 'platinum' (not in the ENUM list).

Why: To test the ENUM('free', 'pro', 'enterprise') constraint.

Validation: The database rejects it with Error 1265. Data truncated. This proves the database strictly enforces valid subscription tiers (Pass).

6. Updating a User's Plan (CRUD)

What is happening: Running UPDATE users SET plan = 'pro' WHERE email = 'partb.user@example.com';.

Why: To test the UPDATE operation and verify data persistence.

Validation: The subsequent select query shows the plan changed to 'pro', proving CRUD operations work correctly.

7. Testing CASCADE Delete

What is happening: Creating a user, session, and message, then deleting the user.

Why: To test the ON DELETE CASCADE constraint.

Validation: The query for the user's sessions/messages after deletion returns 0 rows. This proves the database prevents orphaned data (Pass).

8. Transaction ROLLBACK

What is happening: Starting a transaction, updating a plan, then running ROLLBACK.

Why: To test if the database correctly undoes changes when a transaction is cancelled.

Validation: The final SELECT shows the original state. This proves data is only committed when explicitly told to do so (Pass).

9. Transaction COMMIT

What is happening: Starting a transaction, updating a plan, and running COMMIT.

Why: To test if the database correctly saves changes permanently when instructed.

Validation: The final SELECT shows the updated plan. This proves successful transactions are permanently saved (Pass).

10. Complex JOIN Query

What is happening: Writing a LEFT JOIN with COUNT to find the most active session.

Why: To test the database's ability to handle complex reporting queries (aggregation, grouping, sorting).

Validation: The output lists users, sessions, and message counts. This proves the data structure supports efficient analytics.

11. Debugging SQL Errors

What is happening: Trying to select ak.revoked_at, resulting in Error 1054.

Why: To demonstrate troubleshooting and fixing a broken query.

Validation: Running DESCRIBE api_keys revealed the correct column is status. The query was fixed, proving the ability to debug schema issues.
